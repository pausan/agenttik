# UI

Single page, Vue 3 + Nuxt UI, built by Vite into `web/dist` and served from
`go:embed`. Streaming over `EventSource`.

## Build

The UI is a Vite project in `web/`. `make ui` compiles it into `web/dist`,
which `web/embed.go` embeds; `make build` and `make build-web` depend on it, so
a normal build is still one command. `make ui-dev` runs Vite with hot reload on
:5173 and proxies `/api` — SSE included — to an `agenttik --web` on :7717.

`web/dist` is generated, not checked in. Only `.gitkeep` is tracked, so the
embed directive always compiles and `go build ./...` still works anywhere; a
binary built without `make ui` serves a short notice saying so instead of a
blank page. The cost of the toolchain is node on the build machine and ~260 kB
of gzipped JS in the binary.

Nothing is fetched at runtime. Left to itself, Nuxt UI's icon component
(`@iconify/vue`) fetches any icon it does not already have from
api.iconify.design and two mirrors on first render — slow to fail with no
network, and exactly the kind of external dependency an embedded, offline
tool should not carry. `icon.clientBundle.scan` in `vite.config.js` (off by
default for this plugin, unlike `@nuxt/icon`'s own) scans `web/src` at build
time for every `i-lucide-*` name written as a literal string and bundles just
those. `main.js` also refuses any icon fetch outright, so one that the scan
misses — a name built at runtime rather than written out — renders blank with
a console error instead of hanging the page.

Why a framework at all: the panels are all re-rendered from one state object,
which is what a reactive runtime does for free, and the parts that were most
awkward by hand — a grouped model picker, modals, tab strips with keyboard
handling — are components Nuxt UI already ships.

## Scrollbars

The app shell isolates pane resize handles and scrollbars from portalled UI.
Scrollable panes, popup content, and transcript code blocks and tables also
use isolated stacking contexts. Menus, tooltips, select lists, popovers,
dialogs (including Settings), and slideovers use an explicit `z-50` layer in
the shared Nuxt UI config. Later portals stack above earlier ones, so menus
inside Settings and nested dialogs remain usable. Popup surfaces use solid
theme backgrounds; modal backdrops remain translucent.

Linux Wails windows use CSS-drawn scrollbars with a 10px gutter and themed
thumbs. WebKitGTK with GPU acceleration disabled paints native overlay
scrollbars over opaque popups regardless of stacking order; CSS scrollbars
follow the page's paint order. The `desktop-linux` root class is applied only
when the Wails runtime is present on Linux. Browsers and other desktop
platforms retain their native scrollbar appearance. Scrolling stays native.

## Launch

The shell mounts empty, then `init()` fills it. Providers, projects, sessions
and schedules do not depend on one another's answer, so they are fetched
together rather than one after another. Only then is the last reload's set of
open tabs restored, one at a time and in that same order — sequentially, not
in parallel, because a file tab needs its owner to already be open to
reattach to it, and a project or task tab is its own handful of requests.

A launch still sitting on that empty shell a second later — many restored
tabs, a cold disk — gets a centered spinner over the whole window instead of
looking stuck; one that finishes before the second is up never shows it.

## Look and feel

Nuxt UI's own components and design tokens, with Tailwind v4 utilities for
layout. The palette is an accent over a grey, both chosen in Settings — see
[Colours](#colours) — and both defaulting to blue over a `zinc`
grey. Dark mode follows the system and can be overridden per profile in each browser.

agenttik's green is declared in `main.css` as a Tailwind palette, `agenttik-50`
… `agenttik-950`, rather than as an override of `--ui-primary`, so it is one
more choice in the picker instead of a special case beside it. `@theme static`
emits the whole ramp because the shade Nuxt UI reads — 500 in light, 400 in
dark — is decided at runtime, where Tailwind cannot see it.

A handful of things are still hand-written, in `main.css`: button cursors, the
streaming cursor, the `direction: rtl` trick that moves a path's ellipsis to
the front, the `.markdown` rules that style the tags a rendered reply is built
from — Nuxt UI's reset strips the browser's own spacing, so headings, lists,
code and tables need it back — and the file editor's two stacked layers, its
token colours and the side-by-side diff cells. The token colours are written
out as literals rather than taken from Tailwind's palette: they are the one
set of colours the accent picker must not move, and a `var(--color-*)` that
Tailwind decides is unused resolves to nothing at all.

Enabled buttons use a pointer cursor. Draggable project rows retain grab and
grabbing cursors so their reorder affordance remains clear.

Components read `S` and call actions; none of them touch the DOM directly,
except `Splitter`, whose whole job is a pointer drag. A listing that arrives
while the folder field is being typed into is dropped rather than allowed to
overwrite what was typed.

`Message` is a component of its own for a reason beyond tidiness: a streaming
turn grows the last message a few characters at a time, and inlined bubbles
would all be re-rendered — and re-parsed as markdown — on every delta. As a
component only the one whose content changed re-renders.

## Layout

At widths of 768px and above, the app uses the resizable grid below. Phones
below that breakpoint have a full-width working pane, a project menu, a New
task button, and an on-demand workspace drawer. See [055](055-mobile-layout.md)
for navigation, touch controls and viewport sizing.

```
             ↕ draggable                     ↕ draggable
┌────────────┬──────────────────────────────┬──────────────┐
│ Workspace  │ 1 fix login × 2 agenttik ×   │ Changed      │
│ [repo ▾]   │            [model][effort][◔]│ Commits      │
│ Projects   │  transcript                  │              │
│ Tree       ├──────────────────────────────┤  ...panel... │
│ ...list... │ prompt  [model][effort][cog] │              │
└────────────┴──────────────────────────────┴──────────────┘
```

In the desktop grid, neither sidebar is fixed. A one-pixel `Splitter` sits
between each one and the centre; dragging it sets the width, releasing saves
it to `localStorage`, and the arrow keys nudge it 16px at a time. The grab area reaches a few pixels over
both neighbours so a one-pixel line is actually catchable, without taking any
layout space. Widths are clamped (left 180–520, right 200–620) so a panel
cannot be dragged away entirely.

## Tabs

Each project strip has one leading **context tab**. It shows the project page, one selected task or one scheduled job; selecting another of the three replaces that first tab. The context tab is the only page-or-task-or-job tab in its strip. Files, diffs and other independent views remain separate tabs to its right.

**The strip is one project at a time.** It shows the selected project only. `Alt` and a project's letter lands on that project's work — the task it was left on, or the first in its task list — while a click on its row opens the project page. A project with no tasks opens its page either way ([008](008-project-workspaces.md)).

Tabs use one colour per kind: project pages are sky, tasks green, files amber, and schedules violet. File tabs keep their click-to-preview and double-click-to-keep behaviour ([016](016-file-tab-reuse.md)). The context tab is always inserted before the independent views.

A task title and a job title are both a line of prose ([020](020-task-titles.md), [028](028-scheduled-jobs.md)), so the strip cuts either to 32 characters, including the trailing `...` when needed. The whole title stays the tab's accessible name and its tooltip, so a cut tab is still the one that can be pointed at and read. Project and file tabs are named by a folder and a file and are left alone.

A `+` at the end starts a task in the selected project. `Ctrl+W` closes only the tab in front, including the context tab; it does not close other tabs.

The first nine active tasks in the selected project's sidebar list are numbered top to bottom. **Alt+1 … Alt+9** opens those tasks in the context tab and focuses the prompt. **Ctrl+PageUp** and **Ctrl+PageDown** move through every project, scheduled job and task in the sidebar, top to bottom across every project rather than only the selected one, wrapping at both ends. **Ctrl+Tab** moves right through strip tabs and **Ctrl+Shift+Tab** moves left, wrapping the same way.

What the centre shows, and what the right panel offers, follow the tab in
front:

| Tab | Centre | Right |
|-----|--------|-------|
| Task | transcript, prompt bar, header Stats popover | `Changed \| Commits` |
| Project | `Tasks \| Stats`, no prompt bar — see [030](030-project-tasks.md) | `Project Options \| Changed \| Commits` |
| Schedule | its clock and the runs it spawned | nothing — see [028](028-scheduled-jobs.md) |
| File | `Edit \| Diff \| Preview`, its own status bar | whatever the tab that opened it has |

A file belongs to the view it was opened from, so reading one keeps that view's
right-hand panel rather than emptying it. What it does not keep is the prompt
bar: a file has its own footer, and a prompt box under one is only in the way.
It belongs to its project as well, which is what keeps it on the right strip
once the view it came from is closed — or when it was opened with nothing else
open at all.

**Left — bottom:** a Settings button, always visible under every tab, between a
folder-plus icon that opens the Add project dialog and a keyboard icon that
opens Settings on its Shortcuts section. Adding a project is reachable from
every tab this way, so the Projects list is nothing but projects.

**Right — the workspace header:** **Workspace** appears above the inspector panes.
A repository selector appears only when the current project contains multiple
Git repositories. It changes the repository used by Changed and Commits.
A single repository is selected automatically, with no selector. The left
sidebar selects projects through its project rows. See [053](053-workspace-repositories.md).

**Left — the Projects pane:** project name, folder underneath in small grey,
then all of its still-open tasks in the project's own order. A project added
lands below the ones already there. Projects and those task rows can be dragged
to reorder them. The selected project — the one whose tabs the strip is showing
— is highlighted, and a project with a task mid-turn pulses a dot on the right
of its name, whether or not that task is the one on screen.

The first eight rows carry the letter that reaches them, dimmed and in front of
the name, the way a tab carries its number: **Alt+A** is the top project,
**Alt+B** the next, and dragging a project changes its letter with its place.
Below the eighth there is no letter, though **Ctrl+PageUp** and **Ctrl+PageDown**
still reach it in sidebar order. A letter lands on that project's latest task,
where a click on the same row opens the project page. The letter of the project
already showing folds its tasks away, and folds them back out, so one chord both
reaches a project and shuts it. A one-pixel rule separates each project block from the
next; see [042](042-sidebar-project-rows.md).

A task row of the selected project carries its top-to-bottom number. The first
nine rows are reached with **Alt+1** through **Alt+9**. **Ctrl+PageUp** and
**Ctrl+PageDown** reach every row in the sidebar — project, scheduled job and
task alike, jobs above tasks as the sidebar draws them — top to bottom across
every project rather than only the selected one. Rows of
other projects keep the number column too but carry no number, so titles do
not shift sideways when the selection moves.

Hovering a task row shows the prompt it was opened with, in a tooltip 600px wide
at most, clamped to five lines with an ellipsis on the last one it kept. A title
is three to seven words the model chose, which is not always enough to tell two
tasks in the same project apart. The prompt travels with the row rather than
being fetched on hover, and is capped at 600 characters in SQL — more than five
lines hold, so the rest would only weigh down every listing. A task still
waiting behind another turn has no message of its own yet, so the prompt in its
queue stands in.

Clicking a task opens it with the cursor in its prompt box, in every list that
offers one — the sidebar, the project page's Tasks tab, and a scheduled job's
runs — since picking a conversation is a prelude to typing in it and the focus
would otherwise stay on the row that was clicked. `pickTask` is the one way in,
so a click ends where **Alt+1 … Alt+9** already did. The focus is asked for
after the switch has been drawn, for the reason [025](025-blank-task-reuse.md)
gives: coming from a project page, the click is what mounts the prompt bar, and
a request made before it mounts is watched by nobody.

Clicking a project selects it, which is what puts its tabs on the strip;
clicking the one already selected opens its page, which is the way back to it
once tasks are open on top. The chevron beside the name is its own button and
only expands or collapses the task list. A task row carries a rename pencil and
an archive icon — or **Stop**, while it is running or holding queued prompts
([021](021-stop-active-tasks.md)). Starting a task and deleting a project remain
in the project's own view.

**Left — the Tree pane:** the files of the project that owns the active task,
project, or file tab, and of the selected project when nothing is open in it.
Selecting a project therefore switches Tree to it. With no project selected at
all, Tree asks the user to pick one.

Opening Tree focuses its filter, including when the pane is already in front.

**Centre — task:** the transcript, with the prompt box at the bottom carrying
the shared model control, its separate effort select, the favourite toggle and the context cog. The top
status row carries a pie-chart button immediately after model effort. It opens
task Stats in a compact popover; Agent time, Started, and Last message are the
first three rows. Last message is the timestamp of the newest stored transcript
message, and reads `never` before there is one.

**Centre — project:** its name, folder and a New task button over four tabs.
**Tasks** is every task the project has — open ones in the dragged order, then
archived ones in grey, newest first — behind a filter and a pager
([030](030-project-tasks.md)). **Stats** shows totals plus daily tasks-created
and agent-time charts.

Rows are dragged with the browser's own drag and drop. The list reorders under
the cursor as you go, so where a row is when you let go is where it lands, and
the order is sent once on drop; if the server refuses it goes back to where it
was. Positions are written 1..n, and a project or task created afterwards takes
the next number, so a new row lands at the end of the list rather than on top of
an order the user arranged.

**Right — task:** `Changed | Commits`.
- Changed — staged and unstaged files in the selected repository, with staging
  controls and an expanding commit composer. See [063](063-staging.md).
- Commits — the same branch history offered on a project page.

Task Stats no longer consumes a workspace pane. Its header popover shows model,
effort, permission mode, turn count, context, input/output/cache tokens, cost,
total agent time, task started, and last message. Dates are UTC
`YYYY-MM-DD HH:mm:ss` timestamps.

**Left — the Tree pane:** a real tree, folders before files. Folders start
collapsed. Expanded paths are saved per project in local storage, surviving
project changes, switching sidebar tabs, and program sessions. Right-click a
folder for **Expand recursively**, or empty space to expand the whole tree.
This also expands ignored folders and saves the result.

Clicking a row highlights it. Up/Down move focus and selection through visible
rows without opening files; Enter opens a file. Left collapses an open folder,
or moves to its parent; Right expands a folder, or moves to its first child.
Ctrl+F (also Cmd+F) within the tree focuses its filter. Escape in the filter
clears it and keeps focus there.

A filter box sits above it and narrows the tree on every keystroke — nothing is
fetched, the listing is already here. It matches the **whole path** with the
same subsequence rule as the folder picker, so `wesst` finds
`web/src/store.js`, and the letters it matched are highlighted wherever along
the path they fall, in folder names as well as file names. A folder shows the
letters every match beneath it used. Folders with nothing left are dropped, and
a filter temporarily opens matching ordinary folders without changing saved
expansion. Manual toggles are saved, including during filtering; a closed
matching ordinary folder is revealed again when the query changes.

`tree.js` holds both halves: building the tree once per project, and filtering
it per keystroke. The build is memoised on the listing, so typing only pays for
the filter. What `.gitignore` covers is listed too, drawn grey and shut; see
[027](027-ignored-files-in-the-tree.md).

Files are also made, renamed and deleted here: a right click offers New file,
New folder, Rename and Delete, and F2 renames the row the keyboard is on. Each
asks first, and open tabs follow what moved — see
[046](046-tree-file-actions.md).

**Right — project:** `Project Options | Changed | Commits`.
- Project Options — rename, repoint the folder by typing or by browsing for one
  ([040](040-editable-project-path.md)), New task, Archive project, and Delete
  project behind a confirm ([041](041-project-archiving.md)). Deleting drops its
  tasks and history; the folder is untouched either way.
- Changed — the selected repository’s staged and unstaged files, with the same
  staging and commit controls as a task.
- Commits — the branch log, a commit's files, and their diffs
  ([013](013-project-logs.md)).

## Tasks

Every task row carries a pencil, which turns its title into a field in the row
itself rather than a dialog: Enter or clicking away saves, Escape puts the old
name back, and an empty name is left as no change instead of a task with no
title at all. The title belongs to the task, not the row, so it is re-read
everywhere it shows — the sidebar, the project's page, and the tab strip, whose
label is set directly because a task with no row on screen is in no list that
would carry the new name back. While the field is open its row stops being
draggable: selecting text in it would otherwise reorder the list.

**F2** opens that same field for the current task, from anywhere in the app.
It is always the sidebar's own row that opens: the left panel switches from
Tree to Projects and unfolds the task's project first, whichever of those it
needs. With a scheduled job's page in front it opens that job's row instead —
a job is named and renamed exactly as a task is ([028](028-scheduled-jobs.md))
— so one chord covers both rather than one of them needing a second.

A task row carries an archive icon. Archiving it takes the task out of the
sidebar and closes its tab; it waits, grey, in the project page's Tasks tab,
where the restore icon brings it back ([030](030-project-tasks.md)). Nothing is
deleted. A running task shows **Stop** instead
([021](021-stop-active-tasks.md)), and an untitled one with nothing in it is
deleted rather than archived ([007](007-task-closing.md)).

A new task asks nothing. It opens empty on the model, effort and permission the
newest task in that project was using, kept per project in `localStorage` so a
reload does not lose it; failing that, the newest task in the project, then a
starred combination, then the first installed
CLI. Anything stale — a CLI uninstalled, a model retired — is skipped rather
than used to start a task that cannot run. The model and effort are changed in
the prompt bar afterwards, which is faster than a dialog before every task. Its
prompt textarea receives focus as soon as the new task opens.

Every way in stops at a task that is already blank — nothing said, nothing
queued, nothing typed — rather than opening a second one beside it, and the
search covers the whole project rather than only the tab in front; see
[025](025-blank-task-reuse.md).

Started while a project page is in front, the new task takes that tab's place in
the strip rather than opening beside it. A project page is where a task is
started from — its New task button, the right panel's, the tab strip's `+`,
`Ctrl+N`, or the launcher's — so it hands the tab over instead of staying open
behind the task it just started. Anything opened from the project page goes with
it, as with any closed tab. A file in front is not a project page, so reading
one and starting a task leaves the project where it is.

### Drafts

An unsent prompt belongs to the task, not to the prompt bar. One bar serves
every task, so text left in it would otherwise follow you from tab to tab;
instead each task keeps its own, and switching away and back finds it where it
was left, empty task or not.

It outlives the tab as well, which is what a project's single context slot
([008](008-project-workspaces.md)) demands: opening a project page, or another
task, drops the very tab the text was typed into. `S.drafts` keeps it by session
id as that tab goes and `openTask` hands it back, so an untitled task someone
typed a paragraph into and then clicked away from is still holding it — and
`Ctrl+N` starts a new task rather than reusing that one, because text in the box
is a claim on it. Closing or archiving the task is the one thing that throws a
draft away.

Drafts are saved with the open tabs, the tabless ones included, so a reload does
not lose them either, and the saving is debounced because a keystroke is not
worth a trip through JSON. Once startup finishes, leaving or reloading the
page flushes the current tabs and drafts so it cannot outrun that debounce.

## Files

A file tab has three views on a toggle in its header — **Edit**, **Diff** and,
for markdown and HTML, **Preview**. The choice is remembered rather than reset
per file: reading one diff usually means the next changed file wants a diff
too, so the next file opens the way the last one was left. A file that renders
as nothing has no Preview to offer and falls back to Edit. Only the view being
shown is fetched, and each is fetched once.

**The bar underneath is the file's own.** A task's prompt box has no
business under a file, so the centre leaves it out and a status line takes its
place: the language, whether the file is read-only or has unsaved edits, and
either its line count or the diff's `+`/`−` totals.

### Edit

The file is editable in place, with syntax colouring. An edited tab carries a
`*` beside its path in every view, and the header offers a **Save** button on
Edit alone: a diff and a preview are not where text is typed, and a file with
no editor — an image, a binary, a commit's revision — never offers it at all.
`Ctrl+S` still saves the file in front whichever view it is on, since the edits
are on the tab either way. Tab indents rather than leaving the field. Edits
live on the tab, so switching away and back finds them where they were left,
and only closing throws them away — after asking. Closing a file with unsaved
edits, or a task with such a file open beneath it, offers **Save**, **Don't
save** and **Continue editing**; saving that fails leaves the dialog up rather
than discarding the work. Edits are not written to browser storage — that would
put a working copy in `localStorage` — so a reload is guarded by the browser's
own warning instead.

What was not read whole is never written back: a binary file, or one past the
2 MiB read limit, is read-only in the UI and refused by the server, since
saving the prefix that was read would destroy the rest. A save is atomic — a
temporary file in the same directory, then a rename — so a failed write leaves
the original in place, and the file keeps its own permission bits.

Colouring is `highlight.js`, hand-written for the same reason as
`markdown.js`: the escape function *is* the safety boundary, so no project
file can reach the DOM as markup. It is a lexer, not a parser — comments,
strings, numbers, keywords, calls, tags and attributes — over the C family,
Go, Python, Rust, shell, SQL, JSON, YAML, CSS, markup and markdown, chosen by
extension. Lines are memoised on their text and the state they start in, so a
keystroke re-colours the line under the cursor and reuses every other one;
past 400k characters the file is shown as plain text rather than paying for
the first pass.

The editor itself is a transparent `<textarea>` over a coloured copy of the
same text. Both layers wrap identically, in the same font at the same size, so
they stay aligned with no scroll syncing; the textarea is the layer in flow,
sized to its own content, so revealing the caret scrolls the pane rather than
the field.

### Diff

The file header’s **Expand diff** button fills the app window with the diff,
hiding both sidebars, their splitters, the tab strip and the mobile header.
**Restore diff** or Escape returns to the regular layout with the same sidebar
widths. Text and image diffs support expansion. Switching tabs, projects or
file modes exits expansion; it is not saved between launches.

The diff comes from git: `git diff HEAD` for a tracked file, which folds staged
and unstaged changes into one view, and a comparison against an empty file for
an untracked one, which reads as entirely new rather than as no change at all.
A repository with no commits has no `HEAD`, so there the index is the baseline.
The render stops at 4000 lines — a rewritten file is not read to the end.

It is shown **Unified** or **Split**, on a toggle of its own that is remembered
the same way. Both come from one parse in `diff.js`, so the toggle costs a
re-render and no fetch. Unified keeps git's `+`/`-` markers, because without
them a line says nothing. Split drops them and the file headers: a run of
removals lines up against the run of additions that replaced it, one row at a
time, with blank cells opposite whichever run is shorter, and which column a
line is in already says which side it belongs to. Line numbers come from the
hunk headers and sit in a gutter that copy does not pick up.

Saving drops the tab's diff rather than patching it — the working tree has
moved, and git is the only thing that knows what it now says — and refreshes
the right panel's Changed list.

### Preview

Markdown goes through the transcript's own renderer. HTML cannot: it *is*
markup, so it goes in a fully sandboxed iframe — no scripts, no same-origin,
no navigation. The cost is that relative images and stylesheets do not
resolve, which is the right trade for previewing a file the agent just wrote.
Either way the preview reads the tab's current text, so it follows the editor
rather than the disk.

## The transcript

Agent replies are markdown, so they are rendered: headings, lists, tables, code
blocks, quotes, links, and the inline forms. What you typed is shown as you
typed it, and a tool line stays a literal command.

`markdown.js` is hand-written rather than `marked` plus a sanitiser, for one
reason: there the escaping **is** the parser. Every run of source text goes
through the escape function and the only tags emitted are a fixed list, so no
sanitising pass is needed to know that nothing an agent writes can reach the DOM
as markup. Links drop any scheme that could do something when clicked and open
in the browser rather than navigating the app away; an image renders as its
link, so the transcript still fetches nothing at runtime. It costs about 200
lines and no dependency, and the parser bugs a small one invites are what
`markdown.test.js` is for.

## The context gauge

The cog on the prompt bar opens how full the model's context is: a bar, a
percentage that turns amber past 70% and red past 90%, the token count against
the model's window, and the task's totals underneath.

Used is the size of the last prompt the CLI sent, cached blocks included — not
a sum over the turn. See [002-data-model.md](002-data-model.md#metrics) for why,
and where the number comes from. The window comes from the provider's model
list; a model whose window is unknown shows the count without a total. It moves
while a turn runs, on the provider's own mid-turn usage reports.

## Live updates

**One connection carries every open tab.** `/api/stream` takes the session ids
and project ids to watch in its query, and the UI reopens it when a tab opens or
closes. A stream per tab would be the obvious design and is the wrong one: a
browser holds only a handful of connections to one origin, so a dozen open tasks
would use them all up and stall the API.

A session topic carries its own turn. A project topic carries the start and end
of every turn run in it, from any number of tasks at once.

**One topic is subscribed unconditionally: `projects`.** It carries "a project
was added", from `agenttik --init` in a terminal ([044](044-command-line.md)) or
from another browser tab, and the window that most needs to hear it is the one
with nothing open yet — a fresh install showing "No projects yet". So the stream
is opened even when there is no session, no project and no folder to name, and
the event names no project: the sidebar re-reads its list whole, which also
resubscribes the stream to the project that just arrived.

**Every project is subscribed, not only the ones with a page open.** The sidebar
draws a status dot per task, and a project shows one task at a time — so most of
those tasks have no tab, and a task loses its own as soon as another replaces
it. Their turns can only be heard through their project. Without that
subscription a dot froze at whatever the last full read of `/api/projects` said:
a queued prompt that started stayed grey for the length of its turn, and a task
that finished went on pulsing.

A turn starting or ending re-reads the sidebar's projects whether or not that
task has a tab, and reloads any open project page for its totals. Both are
debounced: a busy project ends several turns at once, and each event arrives
twice — once on the session's topic, once on its project's. The repeat is
dropped by session, turn and kind, so the transcript work behind it runs once
too.

Answers to `/api/projects` can arrive in any order, since a turn event, a tab
opening and a drag landing all ask for the list. Only the newest is kept; an
older one would put a stale dot back on the sidebar until the next event.

`?watch=<project>` names the project the window is showing. It subscribes to
that project's files topic and, while the connection is open, has the server
watch the folder — so the Tree and Changed follow an editor or a `git commit`
outside agenttik. See [019](019-file-watching.md).

## Adding a project

The Add project dialog opens on a **Folder | Multiple Git Repos** switch: a folder that
already exists, or a base folder with one or more repositories cloned into it
as they are named. Either way it ends as one project on one folder — see
[049](049-project-creation-modes.md).

Under the switch is a path field and a folder browser, fed by
`/api/fs`. Clicking a folder walks into it and fills the field (with a trailing
slash, ready for the next keystroke); the breadcrumb walks back up, a home
button jumps to `$HOME` and a folder-plus button makes a folder here and walks
into it. Dot folders are hidden behind a checkbox.

The field can also be typed or pasted into. It is split at the last `/`: the
part before it is the folder to list, the tail fuzzy-filters that listing, so
`~/gh/att` lists `~/gh` and narrows it to `agenttik`. A match needs the tail's
letters in order, case-insensitively; matches near the start and close together
rank first and the matched letters are highlighted. Enter takes the best match
and walks into it, so a folder can be reached by typing alone; with nothing left
to filter, Enter adds the project. A folder that does not resolve is left alone
rather than flagged. The listing is cached per folder, so filtering as you type
does not re-hit the server.

One level is fetched at a time rather than a whole tree: a deep home directory
is far too big to send, and the browser only ever shows one level anyway.

## Shortcuts and file search

`Ctrl+N` and `Ctrl+T` create a task in the project that owns the active tab.
`F2` renames the current task, or the scheduled job whose page is in front —
the same field its sidebar pencil opens.
`Ctrl+Shift+P` opens **Command Palette**, a fuzzy launcher for Projects, Tree, the
active (not archived) tasks, Changed, Task stats, New task, Add project,
Settings, Keyboard shortcuts, and the current task's favourite
model-and-effort combinations. Its filter is `fuzzy.js`, not the command
palette's own fuse search: a row survives when its label *or* its description
contains the typed letters in order, `fuzzyAny` ranks it by the better of the
two, and the letters matched in the label are highlighted the way the tree and
the folder picker highlight theirs. Sections keep their declared order, and the
filter is cleared when the launcher closes.

`Ctrl+P` opens **Go to file**, a fuzzy search of current-project file paths.
Enter opens the selected file in Edit, or Preview for images and fonts.
See [015](015-settings-shortcuts.md) for matching and tab behavior.

`Ctrl+W` closes the tab in front, including a file or project tab, and only that
tab. It does not close files opened from a task, does not archive or delete the
task, and never closes the browser tab; a held chord still closes only once. The
tab strip's `×` keeps its cascade for dismissing a task and its opened files.
`Ctrl+Shift+T` restores closed tabs newest-first for the active project; an
archived task is unarchived and reopened when restored. `Ctrl+Z` and `Ctrl+Y`
undo and redo text in the file editor and the prompt. `Ctrl+S` saves the file in
front, from anywhere on the tab rather than only from inside the text.

`Alt+P` and `Alt+T` switch the left strip to **P**rojects and **T**ree; Tree
focuses its filter. `Alt+1` through `Alt+9` open the matching numbered task in
the selected project. `Ctrl+PageUp` and `Ctrl+PageDown` move through every
project, scheduled job and task in the sidebar, top to bottom, wrapping at
both ends.
`Ctrl+Tab` and `Ctrl+Shift+Tab` move right and left through the project strip.
`Alt+A` through `Alt+H` switch project by sidebar position, onto its latest
task, and repeat on the project already showing to fold and unfold its tasks.

`Enter` queues the prompt and `Ctrl+Enter` sends it; `Shift+Enter` makes a
newline. General swaps the first two ([017](017-general-settings.md)).

All of it is one registry, `shortcuts.js`: the handlers ask `hit(e, id)` rather
than spell a key out, and Settings lists and edits the same entries, so the
list cannot drift from what the app answers to. See
[015](015-settings-shortcuts.md) for the chord format,
what is rebindable and what is not. Chords the window manager or the browser
claims first, `Ctrl+PageUp` and `Ctrl+PageDown` among them, reach the app in
the desktop window; a browser tab may keep them for itself.

### Appearance

**Color mode** offers **Light**, **Dark**, and **System** (the default) through
a `USelectMenu`. Changes apply immediately and persist per profile in each browser.
`color-mode.js` uses VueUse with a profile-scoped storage ref. Default keeps the
existing `vueuse-color-scheme` key; private mode stores its preference in memory. System follows the device's
appearance live, including any schedule configured on the device; the app does
not set its own times. Explicit Light and Dark choices override device changes.
The selector participates in the settings filter, including day and night.
Nuxt UI's surface, text, border and accent tokens and the editor's syntax colours
adapt together. Native controls and scrollbars use the matching `color-scheme`.

A row of swatches for the accent and a row for the grey. Clicking one recolours
the whole app at once, because there is no way to choose a colour but to see
it; the choice is kept in profile-scoped `localStorage` and applied in `main.js`
before the app mounts, so a reload is never painted in the old palette first.

A colour is picked by **palette name**, not by hex. Nuxt UI keeps one reactive
style tag that maps `--ui-primary` and the whole neutral scale onto a Tailwind
palette — shade 500 in light mode, 400 in dark — so setting two names in its
app config is the entire switch, and every component follows on its own.
`theme.js` is the only file that touches that config.

The accents are agenttik's green and seventeen of Tailwind's hues, in wheel
order; the greys are Tailwind's five, `slate` through `stone`. Each entry
carries its swatch class written out, because Tailwind only emits the colours
it can see in the source, and a class built from the name is invisible to it.
Tailwind's own `neutral` swatch is `bg-old-neutral-500`: Nuxt UI takes the name
`neutral` for the grey in use, so `bg-neutral-500` would draw the selected grey
five times over. A stored name that is no longer offered is dropped rather than
passed on, since an unknown palette resolves to no colour at all.

### Models

Under Models the dialog lists every `Subscription · Provider` group with
whether its CLI is on PATH. An eye on the group hides all of its models from
pickers; an eye beside each `Subscription · Provider · Model` row controls that
model alone. Opening the dialog re-reads providers, favourites and visibility,
so changes and newly installed CLIs show without a restart.

The same pane lists favourites in their picker order. Drag handles reorder them on drop; Up and Down arrow keys on a focused handle
also move a favourite. Reordering is disabled while searching. A remove control
with space before the scrollbar deletes one. Favourites are added only from
the main prompt's favourite button. Each combination contains subscription,
provider, model and effort and is shown as `Subscription · Model · Effort` in
the picker. The picker itself is [033](033-prompt-model-picker.md).

Every path parameter under `/api/projects/:id/` is resolved against the project
root and rejected if it escapes it. `/api/fs` is the deliberate exception: you
are choosing which folder becomes a project, so it browses anywhere the user
can, and returns directories only; `/api/fs/dir` and `/api/fs/clone` write
into whatever it reached, which is why each guards its own argument — a folder
name of one segment, a clone URL matched against git's remote forms. The server binds to `127.0.0.1` by default
and has no authentication — it is a local tool.
